# Правила проектов

## Структура кода

- один файл — одна логическая функция, один `def`.
- имя файла коротко описывает, что делает функция.
- имена файлов и папок — транслит русского, snake_case, без пробелов и кириллицы: `osnovnoi_fail`, `parser_zaprosov`.
- папки называются по содержимому: `api`, `main`, `auth`, `parser_zaprosov`.
- для общепринятых вещей можно использовать понятные имена: `api`, `main`, `auth`.
- если у сущности есть своё название — использовать его; если нет — транслит.
- не складывать несколько функций в один файл и не создавать общие папки вроде `utils`, `common`, `misc` без необходимости.
- если функция разрастается — выносить части в отдельные файлы и функции.

## Размер

- ориентир для файла и функции — 20–30 строк.
- больше — только если это действительно оправдано.
- одна функция — одна ответственность.

## Значения и данные

- не хардкодить значения в коде.
- все значения, тексты, локали, таблицы, маппинги и справочники выносить в JSON, YAML, CSV или отдельный конфиг.
- значения должны меняться в одном месте, а не искаться по всему коду.
- если значение используется больше двух раз — вынести его в понятно названную переменную или константу.
- имена переменных и констант должны отражать их смысл.

## Пайплайны

- у каждого модуля свой пайплайн, который запускает его проверки и сборку.
- один общий пайплайн проекта запускает пайплайны всех модулей.
- редкое исключение — компонент без пайплайна, если он действительно не нужен.

## Комментарии

- комментарии только на русском.
- писать кратко, с маленькой буквы, о том, что происходит понятным языком без кода, только описание какое действие происходит и почему.
- маркер комментария — `#`, это правило только для Python.
- не комментировать очевидное.

## Работа агента

- перед изменениями читать этот файл и инструкции конкретного модуля.
- не менять чужие модули без необходимости.
- соблюдать границы папок и не смешивать слои.
- новые значения сразу выносить в данные или конфиг.
- перед завершением проверять пайплайн изменённого модуля и всех правил перечисленных тут.

## Дополнение

- проект всегда должен содержать venv, все что устанавливается должно быть запущено через venv и настроено там. никаких лишних грязных установок в основной компьютер или записей в /tmp и подобные пути. либо по усмотрению пользователя если есть необходимость. 

## Проектирование дизайна

- по возможности использовать скилл `impeccable` (Impeccable) при проектировании дизайна до начала разработки, а при необходимости — и после, для проверки и улучшения интерфейса.
- перед применением скилла читать его `SKILL.md` и следовать его инструкциям.
